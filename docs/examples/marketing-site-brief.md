# Fictional worked brief: Harbor Tasks

**Entirely invented example.** This is a compact demonstration of a completed brief, not a real product, customer, deployment or benchmark. Use the complete [English](../../skills/design-marketing-website/assets/marketing-site-brief-template.md) or [Arabic template](../../skills/design-marketing-website/assets/marketing-site-brief-template.ar.md) for your own project.

## Source and scope

Harbor Tasks is a fictional task organizer for small freelance design teams. The accepted sample scope is a local marketing prototype with three meaningful routes. Shared project boards are the only offered capability; invoices and automated billing are out of scope. No public launch, pricing or real contact backend has been approved. The product definition remains the authority; this brief is linked from it.

## Audience, message and goal

The visitor leads a two-to-five-person freelance design team and needs to explain ownership and the next handoff without another status meeting. The site's message is: **“Know the next handoff before you open your inbox.”** This is positioning copy, not a measured savings claim. Success for this prototype means a visitor can understand the workflow and reach the clearly labeled contact demonstration.

## Page copy and behavior

Home H1: “Know the next handoff before you open your inbox.” Opening: “A shared board for freelance design teams that need a clear owner and a visible next step.” Explain the real board capability, show a labeled synthetic example and link to the workflow. Include no customer logos, ratings or savings statistics.

Workflow H1: “From brief to next handoff.” Use three meaningful scenes: collect the brief, name the owner, move work to review. All sample people, project names and cards are fictional. The scene is explanatory UI, not captured production evidence.

Contact H1: “Ask about access.” Show “Demo form — this does not send or save your details” beside the inputs and button. Use only neutral example values during QA. Validation and a local preview confirmation work; no stored signup or message delivery is claimed. Real submission awaits an approved backend and privacy decision.

## Visual direction

Calm planning-desk identity: ample whitespace, precise horizontal alignment and a modest handoff-arrow motif. Use a muted teal accent, warm white background and dark readable text, with the product's chosen typography and rights checked at implementation. Avoid a generic gradient hero or repeated feature-card grid. This example's teal is its own product direction, independent of this skill repository's yellow promotional branding.

Shared navigation, buttons and form styles stay consistent. Use one purposeful transition for a user action, respect reduced motion and avoid continuous decoration. Use the existing project stack; for an empty prototype, recommend a small static-renderable setup and record the decision before implementation. No optional design skill is required.

## Responsive and accessible behavior

Review at narrow phone, wide phone and desktop sizes, plus zoom and long text. Stack the workflow scenes without hiding their meaning. Keep navigation keyboard-operable with visible focus, useful labels and understandable errors. Use semantic headings and adequate contrast. If Arabic is added, specify equivalent content, RTL layout and isolated Latin strings rather than reversing text. Accessibility review remains a set of observed checks, not a conformance certificate.

## Discovery and performance

This local prototype is not a production indexing result. Each route has a distinct title and description. A final domain, canonical URLs, share-image URLs and public sitemap belong to an approved launch decision; do not ship `example.com` as the real canonical. Add structured data only when its type and visible facts fit. No fake prices, ratings, organizations or guaranteed rich results.

Reserve image dimensions, use appropriately sized assets and avoid scripts or fonts that do not serve the content. Measure relevant performance before claiming any score; distinguish lab observations from field results.

## Build/handoff and acceptance

The chosen route is a coding-agent prototype build. A builder handoff could use this same brief and the actual neutral assets; naming local files is not a transfer. Keep the existing app/backend intact.

Acceptance requires opening all three routes directly and through links, exercising the labeled demo form's validation/confirmation, checking responsive and keyboard behavior, inspecting metadata, and reviewing content against the fictional product facts. Fix observed defects and recheck affected outputs. No checks have been executed merely because they are listed here.

## Change impact and open decisions

If real access opens later, review contact copy, form destination, success/error states, privacy text, primary CTAs and relevant metadata together. New billing features must not appear as available before an accepted release decision. Merge the maintenance rule into project instructions when ongoing maintenance is requested.

Open decisions: real submission destination, domain, access policy, final fonts and any production deployment. These are pending sample decisions, not barriers to completing the explicitly local prototype.
